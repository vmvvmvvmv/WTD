# 날씨 RAG 기반 일정별 해설 AI 기획서

## 1. 한 줄 요약

사용자의 캘린더 일정과 실제 날씨 데이터를 합쳐서, 왜 우산·겉옷·마스크가 필요한지 쉽게 설명해 주는 기능을 만든다.

## 2. 기획 배경

현재 WTD는 날씨와 미세먼지 수치를 보여 주고 규칙에 따라 옷차림을 추천한다. 하지만 사용자는 추천 결과만 보고 이유를 모를 수 있다.

예를 들어 `바람막이 필요`라는 결과보다 다음 설명이 더 이해하기 쉽다.

> 오후 일정 시간에 바람이 강하고 체감온도가 낮아서 바람막이를 챙기는 게 좋아요.

RAG를 사용해 날씨 행동 기준과 설명 자료를 참고하게 하면, 매번 프롬프트에 긴 기준을 직접 넣지 않아도 된다.

## 3. 목표

- 일정 시간과 장소에 맞는 날씨 설명 제공
- 추천 결과의 이유를 사용자가 이해할 수 있게 표시
- 날씨 기준은 문서에서 찾고, 현재 수치는 DB·공공 API에서 사용
- AI가 실패해도 기존 규칙 기반 결과를 보여 줌
- 답변에 참고한 기준 문서를 표시할 수 있게 준비

## 4. 대상 사용자와 사용 상황

### 대상 사용자

- 외출 전에 준비물을 확인하는 사용자
- 캘린더에 일정이 등록되어 있는 사용자
- 날씨 수치는 보지만 행동 기준을 잘 모르는 사용자

### 주요 사용 상황

1. 사용자가 오늘 일정 상세 화면을 엶.
2. 앱이 일정 시간대의 날씨·미세먼지·활동 유형을 확인함.
3. 관련 날씨 기준 문서를 검색함.
4. 규칙 엔진 결과와 검색 문서를 Gemini에 전달함.
5. AI가 짧은 설명과 준비물을 반환함.
6. 앱은 추천 결과와 이유를 함께 보여 줌.

## 5. 1차 기능 범위

### 포함

- 캘린더 일정별 날씨 해설
- 실내·실외·이동 일정 구분
- 비·눈·강풍·더위·추위·미세먼지 기준 검색
- 추천 이유 1~2개 표시
- 준비물 요약 표시
- 규칙 기반 결과 fallback
- AI 응답 JSON 검증
- AI 답변 캐시

### 제외

- 날씨 수치 자체를 RAG 문서에서 검색하지 않음
- AI가 미세먼지 등급을 직접 판정하지 않음
- 의료 진단이나 치료 방법을 제공하지 않음
- 처음부터 별도 벡터 DB 서버를 운영하지 않음
- 사용자가 업로드한 개인 문서를 검색하지 않음

## 6. 답변 예시

### 일정별 해설

> 오후 3시 야외 일정에는 비가 올 가능성이 높아요. 우산을 챙기고, 기온이 내려가서 얇은 겉옷도 준비하는 게 좋아요.

### 추천 이유

> 바람막이를 추천한 이유는 일정 시간의 바람이 강하고 체감온도가 낮기 때문이에요.

### 미세먼지 안내

> 미세먼지가 나쁨 수준이라 오래 걷는 일정은 줄이는 게 좋아요. 외출한다면 마스크를 준비하세요.

## 7. RAG에 넣을 문서

처음에는 Markdown 파일로 관리한다.

```text
backend/knowledge/weather/
  rain.md
  snow.md
  wind.md
  heat-cold.md
  air-quality.md
  activity-rules.md
```

문서 내용은 다음 기준으로 작성한다.

- 한 문단에 하나의 기준만 작성함.
- 기준의 출처와 갱신 날짜를 적음.
- 수치 기준은 규칙 엔진과 충돌하지 않게 관리함.
- 건강 관련 문장은 일반적인 생활 안내로 제한함.
- 공식 자료가 아닌 내용은 단정하지 않음.

## 8. 처리 구조

```text
캘린더 일정
    ↓
날씨·미세먼지 DB/API 조회
    ↓
기존 규칙 엔진으로 위험 요소와 준비물 계산
    ↓
일정·날씨 조건으로 관련 문서 검색
    ↓
규칙 결과 + 검색 문서 + 현재 수치를 Gemini에 전달
    ↓
JSON 응답 검증
    ↓
앱에 설명 표시
```

역할은 다음처럼 나눈다.

| 부분 | 담당 내용 |
|---|---|
| DB·공공 API | 현재 날씨, 예보, 미세먼지 수치 |
| 규칙 엔진 | 등급 판정, 준비물 결정, 안전 기준 |
| RAG | 설명에 필요한 날씨 기준 문서 검색 |
| Gemini | 사용자가 읽기 쉬운 문장 작성 |
| 응답 검증기 | 형식·필수 내용·위험한 문장 확인 |
| fallback | AI 실패 시 규칙 기반 결과 반환 |

## 9. 1차 검색 방식

문서가 많지 않으므로 처음부터 벡터 DB를 도입하지 않는다.

### 1단계

- 문서를 문단 단위로 나눔.
- 활동 유형, 날씨 상태, 미세먼지 등급으로 후보를 좁힘.
- 후보 문단 3~5개를 Gemini 입력에 넣음.

### 2단계

문서가 많아져서 단순 검색이 부족할 때 임베딩 검색을 추가한다.

- Gemini 임베딩 사용 검토
- FAISS 또는 Chroma 검토
- 검색 결과 상위 3~5개만 전달
- 기존 규칙 결과와 비교 테스트

현재 GCP 서버가 단일 2GB 서버이므로 벡터 DB용 별도 서버는 1차 범위에서 제외한다.

## 10. 기존 코드와 연결할 위치

- 기존 날씨·미세먼지 조회 모듈에서 일정 시간대 데이터를 가져옴.
- 기존 옷차림 규칙 엔진의 결과를 기준값으로 사용함.
- 기존 `GeminiLLMClient`를 재사용함.
- 기존 응답 검증기와 fallback 구조를 유지함.
- RAG 검색 모듈은 `dust/services/outfit/` 안에 별도 모듈로 둠.

예상 모듈:

```text
dust/services/outfit/
  rag_documents.py       # 문서 읽기와 문단 분리
  rag_retriever.py       # 조건에 맞는 문서 검색
  rag_prompt.py          # 규칙 결과와 검색 결과 조합
```

## 11. 응답 규칙

AI는 아래 구조로만 반환한다.

```json
{
  "summary": "짧은 날씨 설명",
  "reasons": ["비 확률이 높음", "바람이 강함"],
  "items": ["우산", "얇은 겉옷"],
  "source_topics": ["rain", "wind"]
}
```

검증에 실패하거나 AI 호출이 실패하면 기존 규칙 기반 응답을 반환한다.

## 12. 성능·비용 관리

- 같은 일정·같은 시간대의 결과는 Redis에 캐시함.
- 문서 검색 결과는 짧게 유지함.
- Gemini 입력 문서 수는 최대 3~5개로 제한함.
- 기존 하루 AI 호출 제한을 유지함.
- AI를 호출하지 않아도 규칙 기반 결과를 반환함.
- 응답 시간과 AI 호출 수는 실제 서버 배포 후 측정함.

## 13. 개인정보와 안전

- 캘린더 제목은 필요한 경우에만 AI 입력에 포함함.
- 사용자 식별 정보와 API 키는 문서 검색 데이터에 넣지 않음.
- 건강 관련 표현은 진단·치료가 아닌 생활 안내로 제한함.
- RAG 문서에 출처와 갱신 날짜를 남김.
- 실제 수치와 문서 기준이 다르면 규칙 엔진 결과를 우선함.

## 14. 개발 단계

### 1단계: 문서와 검색기

- 날씨 기준 Markdown 6개 작성
- 문단 분리와 조건 검색 구현
- 검색 결과 테스트 작성

### 2단계: AI 입력 연결

- 기존 옷차림 규칙 결과와 검색 결과 결합
- Gemini JSON 응답 스키마 추가
- 응답 검증과 fallback 연결

### 3단계: 앱 화면

- 일정 상세에 `날씨 해설` 영역 추가
- 추천 이유와 준비물 표시
- 로딩·AI 실패·데이터 없음 상태 추가

### 4단계: 운영 확인

- 실제 날씨 조건별 답변 검토
- 잘못된 기준이나 과한 표현 수정
- Redis 캐시 적중과 AI 호출 수 확인
- 실제 사용자 응답 시간 측정

## 15. 완료 기준

- 비·눈·강풍·더위·추위·미세먼지 문서 검색 테스트 통과
- 일정별 날씨 해설이 현재 날씨 데이터와 일치함
